Feature Separation & Integration Plan

One demo, four platforms, and the hub that composes them.

The current product is a single integrated demo that bundles the Digital Twin, the Agentic AI, and the Scenario Engine together — plus new generation features with no home yet. This document separates every feature into the platform that should own it, lays out how to migrate each one, and defines the hub that serves any combination of them as independent, composable services.

01

Where we are, and where this goes

Today everything runs inside one demo application for robustness. That was the right call to ship — but it means the Digital Twin, the Agentic AI reasoning, and the Scenario Engine are entangled in one codebase, and the new 2D→3D and BIM work has no dedicated home. The target is five independent services behind one hub.

Today · one bundled demo

  • Twin engine runs in-process alongside everything else
  • ~30 AI agents live inline in the demo, not in a platform
  • Scenarios & training are a hard-coded library in the app
  • 2D→3D & BIM generation bolted directly onto the demo
  • One UI, one process — pick-and-choose isn't possible
→

Target · five composable services

  • Digital Twin — the live, physics-grounded asset model
  • Agentic AI — every reasoning agent & workflow
  • Scenario Engine — author, run & score what-ifs + training
  • 3D & BIM Generation — image→3D, drawing→3D, IFC→layers
  • Integration Hub — one entry point, composed per customer

The good news: this isn't a rewrite. The Digital Twin platform already exposes a full service API and even carries an integration layer that calls the Agentic AI and Scenario Engine. The migration is mostly de-inlining — lifting each capability out of the bundled demo and back onto services that are already partly built.

02

Each feature, mapped to its platform

Every capability in the product today, grouped under the platform that should own it. The rule of thumb: the Digital Twin owns truth about the asset, the Agentic AI owns reasoning, the Scenario Engine owns what-if & training, and Generation owns turning inputs into 3D.

Digital Twin Platform

The live, physics-grounded model of the asset and its world

Owns the twin, its telemetry, its health, its predictions, and the knowledge graph & BIM that describe it. Everything else asks the twin what's true.

Twin core

  • Twin lifecycle — create, seed, list, start/stop, delete; per-domain templates
  • Domain physics models — Wire EDM, Gas Turbine, Fleet / Tram Network, and a generic model that twins any fed-in network or fleet spec
  • Live telemetry — multi-signal streaming per domain on a real-time ticker

Intelligence in the twin (deterministic, not LLM)

  • Behaviour rules engine — 3-tier (physics-residual → statistical → hard-limit) producing findings
  • Health model — per-component & subsystem health index and status
  • Prediction engine — trajectory projection, remaining-useful-life / time-to-limit, detection timeline
  • What-if projection — non-destructive fault injection & forecast at the physics level

Spatial & semantic truth

  • Diagnostics surface — sensors, subsystems, incidents
  • Fleet network view — live vehicle positions, per-route status, blocked-route propagation
  • Ontology & knowledge graph — classes, SHACL shapes, domain packs, schema/query/write, changelog, topology
  • BIM twin — building elements, discipline mapping, storey structure, fault-to-element (X-ray) overlay
  • Event bus — real-time findings/telemetry stream, the backbone other services subscribe to
telemetryfindingsRUL / predictontology graphBIM semanticsevent bus
Agentic AI Platform

The reasoning layer — every LLM agent and workflow

Owns all language-model reasoning. It reads the twin's state through the twin's API, thinks, and returns diagnoses, plans, narratives and answers. It never simulates physics itself.

Diagnostic & analytic agents

  • Diagnosis agent — root cause from findings + telemetry
  • Analysis agent — present state and forecast, in narrative
  • Cascade / failure-chain analysis — how one fault propagates
  • Predictive alerts — early-warning narration from the forecast
  • Grounded snapshot narration — diagnose & forecast from a state snapshot

Action & operations agents

  • Work-order generation — structured, ordered repair steps
  • Maintenance procedure builder — steps with safety & dependencies
  • Parts procurement agent — parts list from a work order
  • Incident report generation
  • Asset / component status Q&A

Conversational & build agents

  • Co-pilot narration — auto-observations on live telemetry
  • Dashboard chat & troubleshoot chat — live status Q&A
  • Vision → twin spec + build-a-twin conversational agent

Platform capabilities

  • Workflow engine — node graph (AI action, decision, code, integration, trigger, web-search, escalation), executor, templates
  • Agent memory — conversation history & context
  • Local fallback mode — zero-token deterministic generators for resilience & cost control

Scenario Engine

Author, run, and score what-if and training scenarios

Owns scenarios and training end-to-end. It orchestrates a run — driving the Digital Twin's projection and, where relevant, the Agentic AI — then measures the outcome against KPIs.

Scenario authoring & catalogue

  • Scenario library — curated what-ifs per domain
  • Scenario authoring — natural language → runnable spec
  • External-situation presets — heatwave, event surge, signalling outage, storm, and more
  • Fault catalogue — the injectable faults per domain

Run & scoring

  • Run orchestration — drives the twin's projection, collects the outcome
  • World / environment model — events, resolution, catalogue
  • KPIs, results & certification — objective scoring of a run
  • Live run streaming — run manager + websocket updates

Training & guided repair

  • Interactive training simulator — perform / skip steps, consequences, safety & order penalties, score & grade
  • AI Maintenance Director — cinematic autonomous-repair run visualisation
scenario libraryauthoringrun + KPIstraining simcertification
3D & BIM Generation

Turn images, drawings and IFC into 3D

A standalone generation service — its own dedicated space to perfect quality. It produces geometry; the Digital Twin consumes it (attach a model, or map a building's layers).

Image → 3D (TRELLIS)

  • Preprocessing quality gate — isolate / segment / enhance / normalise / frame the subject
  • Sampler quality presets — draft / standard / ultra, exposing the model's real levers
  • Multi-image conditioning — 2–4 views of one object for higher fidelity
  • Mesh post-processing — validate / stats / repair; provider abstraction; production GPU worker

Drawing & building conversion

  • Drawing / floor-plan → 3D scene — furnished, navigable
  • IFC → discipline-layer models — architecture / structure / plumbing / HVAC / electrical / fire, as separable layers
  • Geometry-prior retrieval — catalogue consistency for known assets
  • 19-stage generation pipeline — one spine, object & drawing routes

Integration Hub

The single entry point that composes the four platforms per customer

Not a fifth silo — the connective tissue. It authenticates once, decides which platforms a customer has enabled, and assembles exactly that API and UI. Choose Digital Twin alone and you get only the twin; add Agentic AI and the agent panels appear.

Entry & access

  • API gateway — one entry, routes each request to the owning platform
  • Auth, tenancy & SSO — handled once, for every platform behind it
  • Aggregated health & unified API catalogue

Composition & commerce

  • Capability manifest + entitlements — each platform advertises what it offers; each customer has an enabled-module set
  • Composed API & UI — surfaces built from the intersection of what's available and what's licensed
  • Per-module licensing & metering

Orchestration & delivery

  • Cross-platform event loop — finding → agent → scenario → twin overlay, wired end-to-end
  • Unified shell / micro-frontends — one dashboard, module panels loaded by entitlement
  • Deployment & scaling — one container per platform, independently scalable

04

Migration plan

A strangler-fig sequence: at every step the demo keeps working by calling the real service when it's up and falling back to the current inline code when it isn't. Nothing breaks mid-migration; inline code is deleted only once the service path is proven.

0Contract freeze

Freeze the API contracts

The demo's current API is the de-facto spec. Freeze it as the contract each platform must satisfy, and add a per-platform client to the shell with a "use remote service" flag. This is the switch every later phase flips.

twin contractagent contractscenario contractgeneration contract
1Digital Twin

Point the shell at the Digital Twin service

Stop running twin physics in-process; call the platform instead. Add the two missing surfaces the demo introduced: the fleet network map endpoint and the BIM discipline-layer split. Lowest-risk first move — the fleet physics already lives in the platform.

route twin calls to service+ network endpoint+ BIM layers
2Agentic AI

Lift the agents onto the platform

Port each inline agent into an agent definition / workflow, pulling twin context through the twin's API. Keep the prompts verbatim — they're good — but host them on the platform's executor with its memory. Highest-value move: the agents are the most wrongly-placed capability.

diagnosiswork ordercascadeprocurementchats + memory
3Scenario Engine

Move scenarios & training onto the engine

Migrate the scenario library and authoring into scenario definitions; move training/grading into runs + KPIs. The physics projection stays in the Twin — the Scenario Engine orchestrates the run and scores the outcome.

scenario libraryauthoringtraining runsKPIs
4Generation

Consolidate 3D & BIM into the generation service

Merge the image→3D pipeline, drawing→3D, and IFC conversion into one dedicated service and deploy the production GPU worker. Its output feeds the Twin (attach a model, map a building). This is where 3D quality gets perfected in isolation.

image→3DGPU workerdrawing→3DIFC→layers
5Retire & compose

Delete the inline code; the shell becomes the hub

Once every service path is verified, remove the in-process twin, the inline agents, and the hard-coded scenarios from the demo. What remains is a thin composition layer — the Integration Hub — plus the entitlement manifest that gates it.

05

The hub, composed

The hub's job is "pick what you want, get exactly that." A capability manifest and per-customer entitlements decide which platforms are active, and the hub assembles that API and UI. A few representative bundles:

Digital Twin

Monitoring only. Live telemetry, findings, health and prediction dashboards. No agents, no scenarios — just the twin and its numbers.

Digital TwinAgentic AI

Monitoring + co-pilot. The twin, plus diagnosis, work orders, narration and chat panels appear alongside it. The classic "explain and act on what I'm seeing" product.

Digital TwinScenario Engine

Monitoring + what-if / training. Run scenarios and certify operators against the twin's physics, with KPIs and scoring — no LLM agents required.

Digital TwinAgentic AIScenario EngineGeneration

Full suite. Build a twin from an image or IFC, monitor it, reason over it, and drill it with scenarios — the closed "finding → agent → scenario → overlay" loop.

Capability manifest + entitlements

Each platform publishes what it can do; each customer has an enabled-module set. The hub composes both API and UI from the intersection — one mechanism delivers the entire "choose what you want" requirement.

Gateway + aggregated catalogue

One entry point routes each request to the owning platform, handles auth and tenancy once, and merges every platform's API spec into a single catalogue.

Composed shell, not four tabs

Evolve the existing dashboard into the shell; lazy-load each platform's panels by entitlement so the product feels like one surface, not a switchboard.

Event-driven closed loop

Ride the twin's event bus: a finding triggers an agent, the agent proposes a fix, a scenario validates it, and the result overlays back on the twin — the "Ironman" loop that makes composition feel like one product.

Recommended first move — Phase 1 (Digital Twin) plus the entitlement-manifest skeleton: lowest-risk, and the manifest is the backbone every later phase plugs into.
